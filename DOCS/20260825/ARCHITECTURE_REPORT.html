Tier 1 · Executive summary

30-second read

A WinUI 3 desktop app with a testable engine room and nothing else. All real logic lives in PoChopAudio.Services, which references no UI and no hosting framework; the app project calls it in-process. That single constraint is what lets 93 automated test methods cover the interesting behaviour without ever opening a window.

The architecture is shaped by a history it no longer has. The vertical slices, the chop job store, and Outcome<T> all came from an ASP.NET + Blazor era. They survive because each still earns its place — Outcome<T> is the seam that used to be HTTP status codes — not because a server is coming back.

Tier 2 · C4 Level 2 — container boundaries

Four things run or sit on the user’s machine: the app process, the two libraries it links, and the local resources it touches. Nothing crosses a network boundary at any point.

The rule that holds it together

Services must never reference WinUI or take a dependency on any UI or hosting framework. Its only packages are Microsoft.Extensions.Logging.Abstractions, NAudio, NLayer.NAudioSupport, SixLabors.ImageSharp and Microsoft.ML.OnnxRuntime. That is why both test projects can drive it directly.

The rule between slices

Per NET_RULES §2, slices never reference each other. Services/Chop and Services/Cutout share nothing but Outcome<T> and ExportedFile at the project root; anything two slices need is promoted to Shared.

C4 Level 3 — component map

Request lifecycles

Chop — the stateful shape

ChopService keeps a job store because the expensive step and the cheap step are different steps. Upload decodes once to a canonical 32-bit float WAV; analyze re-runs only detection against that WAV; export renders on demand. Turning a knob therefore never re-decodes an M4A.

Cutout — the stateless shape

CutoutService has no job store at all. The multi-step version existed to give a browser a handle to refer back to across stateless HTTP requests; in-process, the caller already holds the bytes, so the store, its two-hour expiry and its temp directory were pure ceremony.

Why the synchronous methods are synchronous

Analyze, GetClip and the ZIP builders do real DSP and image work. Making them async would not move that work off the calling thread — it would only hide the fact that it stays there. Leaving them synchronous forces the caller to decide, and the view models call them through Task.Run. Call one directly from a WinUI event handler and the window freezes.

// WinUI/Services/ServiceOutcomeExtensions.cs — conversion happens at the consumer boundary only.
public static T OrThrow<T>(this Outcome<T> outcome) =>
    outcome.IsSuccess
        ? outcome.Value
        : throw new ServiceFailureException(outcome.Failure!.Value, outcome.Message);
Direction of the conversion matters

OrThrow() lives in WinUI, not in Services. The services never throw for an expected failure; the view models, which already funnel everything into an ErrorMessage inside one try/catch, opt into exceptions at their own boundary. Pushing that back into Services would destroy the property that makes the library host-agnostic.

Architectural findings

Finding 1 — the Chop slice is unreachable from the UI

PoChopAudio.WinUI.csproj carries <DefaultItemExcludes>$(DefaultItemExcludes);Views\ChopPage.xaml;Views\ChopPage.xaml.cs</DefaultItemExcludes>, so the Chop page is not compiled. MainWindow.NavigateTo consequently hard-codes Type pageType = typeof(CutoutPage); and discards the tag with _ = tag;. The “Chop Audio” nav item is therefore live in the shell and lands the user on Cutout Studio. Meanwhile ChopViewModel (549 lines), ChopService, ChopJobStore, AudioRecorderService and AudioPlayerService all still compile and are registered in DI, and the chop logic remains the most heavily tested code in the repository. This is a UI wiring gap, not rot — but a reader of the nav bar cannot tell.

Finding 2 — two containers are described by their build, not their code

The solution-wide build does not produce a runnable app. The WinUI project needs an explicit platform and RID (-p:Platform=ARM64 -r win-arm64), and the exe must be run from bin, never publish — dotnet publish silently drops PoChopAudio.WinUI.pri and the app dies at startup with a stowed exception (0xC000027B) inside Microsoft.UI.Xaml.dll. The app is also self-contained (WindowsAppSDKSelfContained + SelfContained) because the pinned Windows App SDK 1.6 runtime is not installed on most machines and an unpackaged app without it fails with 0x80670016.

Finding 3 — stale artifacts still name the deleted projects

tests/PoChopAudio.Unit/bin/ and tests/PoChopAudio.Integration/bin/ still contain PoChopAudio.API.staticwebassets.*.json and PoChopAudio.Client.staticwebassets.*.json. They are build output, not sources, and they are the only reason a repository-wide grep for Blazor or Minimal API terms returns anything. A dotnet clean or a fresh clone removes them.
