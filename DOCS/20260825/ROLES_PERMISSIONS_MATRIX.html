Roles & Permissions Matrix

This application has no authentication, no authorization policies and no principals of its own. What it does have is an operating-system consent surface — camera, microphone, file system, temp storage — and that is what this matrix maps, principal by principal and environment by environment.

Scope correction

The NET_DOCS template asks for a grid of code-derived endpoint authorization policies — RequireAuthorization, policy attributes, FallbackPolicy. There are zero occurrences of any of these in the repository, because there are no endpoints: PoChopAudio.API was deleted. AGENT.md states the position directly — “No auth. Nothing is protected, so there is no BFF cookie flow, no Entra ID, no FakeAuthHandler.” An empty grid would be technically correct and useless, so this report maps the access control that is enforced: the Windows consent and token model that governs a self-contained, unpackaged desktop process.

Tier 1 · Executive summary

30-second read

One principal, no roles, and every permission decision is made by Windows rather than by this code. The app runs unpackaged (WindowsPackageType=None) with the invoking user’s token, so it can read and write anything that user can. It declares no MSIX capabilities because it has no MSIX manifest to declare them in.

Two capabilities are gated by the OS at runtime — camera and microphone — and the app handles refusal by catching, reporting and continuing rather than crashing. File writes are narrower than the token allows, because every write path goes through a picker the user drives: the app never chooses a destination on its own.

Tier 2 · Trust boundaries

There is exactly one trust boundary and it is the process edge. Everything inside it — the view models, both services, the ONNX session — runs at the same privilege with no internal checks, because there is no lesser-privileged caller to defend against.

Why there is no capability list

<WindowsPackageType>None</WindowsPackageType> means no Package.appxmanifest and therefore no <Capabilities> element. The only manifest present is app.manifest, and it declares exactly two things: supportedOS for Windows 10/11 and dpiAwareness = PerMonitorV2. No requestedExecutionLevel is specified, so the process runs as the invoking user without an elevation prompt.

Why that is the safer default here

A packaged app would gain a declarative capability list but also a broker, a package identity and a virtualised file system. Unpackaged, the blast radius is exactly the user’s own rights — and every destructive operation the app performs (writing an export, deleting a temp job directory) is already scoped to a path the user chose or a directory the app created.

The pattern, stated once

Probe, report, degrade — never throw at startup. It governs the camera, the microphone, the ONNX model and the platform audio codecs alike. AudioDecoder reports a different extension list on non-Windows because M4A/AAC/WMA go through MediaFoundationReader; CutoutService.IsAvailable goes false when the model is missing; CameraService.StartAsync returns false rather than propagating. In every case the capability disappears from the UI instead of breaking it.

Privacy stance, quoted from the code

HeadFinder’s own doc comment explains why it crops by mask shape instead of adding a face-detection model: “It needs no second model and no face detector, which matters because the same logic has to run in the browser, where photographs of a face must never be uploaded.” The browser is gone; the constraint it produced is still the reason the app can process a photograph of a person’s face without any of it leaving the machine.

If this is ever hosted for more than one person

AGENT.md already names the migration path, and NET_RULES still governs it. Recorded here so the empty grid above is not mistaken for an oversight:

  • Add a Features/Auth slice and a FallbackPolicy; the NET_RULES rules for that path continue to apply.
  • Outcome<T> already carries the mapping — NotFound → 404, Invalid → 400, TooLarge → 413, EngineUnavailable → 503 — so the failure taxonomy survives the move without change.
  • The two services are already host-agnostic and already enforce their own limits, so an endpoint layer would add authorization and nothing else.
  • The temp-directory job model would need replacing: it resets on restart by design and holds no per-principal partition.
